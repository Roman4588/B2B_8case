## Развёртывание и согласованная стоимость

Окончательная штатная конфигурация: commit `5488bed7e0306e3fd04e46e96f03235b7526061e`. Финальная сборка этой конфигурации прошла, CI успешен; digest и CI зафиксированы в [cloud-build.json](amvera-evidence/cloud-build.json). Последующий commit отчёта не меняет код приложения.

Владелец согласовал **490 ₽ за 30 дней**: существующее B2B, Miami-0, тариф «Начальный Плюс», 0,5 CPU, 1 ГБ RAM, 5 ГБ диска. Тариф применён; автоскейлинг выключен. Новые платные ресурсы и дополнения не создавались. [Подтверждение тарифа](amvera-evidence/tariff-applied-2026-10-30.png). Расчёт относится к 30 дням непрерывной работы в пределах включённого диска и трафика; платный сверхлимит не заказывался.

| Служба в одном приложении | Назначение |
|---|---|
| Nginx, FastAPI | Интерфейс, API и сессии, внешний порт 80 через HTTPS Amvera |
| Celery solo worker с beat | Фоновый импорт, индексация, поиск, опрос мониторинга |
| PostgreSQL 17 + pgvector | Аккаунты, инструкции, векторы, события, журнал |
| Redis | Очередь и результаты задач |
| Prometheus 3.5 | Настоящие scrape, правила alerts и HTTP API |
| Учебный exporter | Только синтетические метрики для демонстрации |

PostgreSQL, Redis, Prometheus и exporter слушают loopback. Общий постоянный `/data` обеспечивает фактическую доступность загруженных файлов API и worker. Одна реплика, `singleton: true`, `zeroDowntime: false`: одновременно запускать два PostgreSQL на одном каталоге нельзя.

Штатный CMD — `python -m app.processes standalone`; в Amvera command/args возвращены к пустым значениям. Dockerfile: `deploy/amvera/Dockerfile.standalone`, порт 80, `/data`. Bootstrap ADMIN_EMAIL/ADMIN_PASSWORD уже находились в обычных переменных Amvera; их значения не изменялись и не публиковались. В текущем UI редактирование не позволяет переключить существующую переменную в секрет; для дальнейшего усиления хранения следует отдельно оформить их как секреты либо убрать ненужный bootstrap после безопасного сохранения доступа. Секрет PostgreSQL создаётся один раз в `/data/.postgres-password` с правами 0600. `SESSION_SECURE=true` задан в образе; реальные пароли в Git не сохранены.

Просмотр системного журнала Amvera за последние 30 минут вернул «Лога пока нет». Это не доказательство отсутствия любых системных ошибок вне наблюдаемого сценария. Долговременное отсутствие OOM под произвольной нагрузкой не подтверждалось.

Первый полный публичный прогон остановился на сетевом ReadTimeout одного GET /api/users. Повторная отдельная проверка дала 403 за 0,23 с; затем весь HTTP-прогон прошёл без ошибки. Этот случай не скрыт и не выдаётся за доказательство отсутствия любых сетевых сбоев.

Для пункта 20 оператор временно выбрал отдельный entrypoint `amvera_source_probe.py`: он приостановил ровно Prometheus и учебный exporter на 90 секунд, затем автоматически возобновил их. Приложение сохранило события, показало error и ответило /api/demo 503. Восстановление online наблюдалось без ручного возобновления процессов. Проверяющий entrypoint не вызывается обычным CMD и не доступен через API. Временные command/args убраны, выполнен штатный перезапуск; [штатная конфигурация](amvera-evidence/cloud-final-configuration.png), [окончательное состояние](amvera-evidence/cloud-final-sources.png) и [повторный HTTP-прогон](amvera-evidence/cloud-final.json) сохранены.

## Локальная проверка и исправленные проблемы

61 backend-тест прошёл, 10 отдельных интеграционных тестов в локальном unit-прогоне не запускались. Дополнительно полный HTTP-сценарий выполнен на настоящих PostgreSQL/pgvector, Redis, Prometheus и worker в одном контейнере: [результат](amvera-evidence/budget-local-packaging.json). Проверены отказ источника и перезапуск с сохранением 13 файлов и неизменной исходной SQLite: [результат](amvera-evidence/budget-persistence.json).

Лимит локальной упаковки — 950 MiB без swap и 0,5 CPU, включая пустой `/run`, как в облаке. Итоговый прогон прошёл без OOM; пик около предела, [измерение](amvera-evidence/budget-memory.json). В локальной базе 259 инструкций, PDF обработан за 20,174 с. Это проверка небольшой демонстрационной нагрузки.

Ранние варианты превышали память: подготовка БД вынесена во временный процесс, единственная embedding-модель оставлена в worker, для Prometheus задана мягкая цель памяти Go, sklearn загружается только при необходимости текстовой классификации. Классификация и её fallback покрыты тестами. Эти настройки не меняют обычный Compose.

Первый облачный запуск выявил пустой `/run`: PostgreSQL не мог создать сокет. Ошибка воспроизведена локально; каталог теперь создаётся с владельцем postgres при запуске. Prometheus предупредил о неподдерживаемом NFS, поэтому его временная TSDB перенесена в `/tmp/prometheus`.

## Ограничения

- Это демонстрационный стенд с небольшой нагрузкой. Многопользовательский нагрузочный тест, HA и SLA приложения не подтверждались; запас RAM невелик.
- История метрик Prometheus сбрасывается при замене контейнера. Аккаунты, инструкции, события, ручной журнал и файлы остаются в постоянном `/data`.
- Мониторинг использует синтетический exporter и настоящий Prometheus; к рабочей инфраструктуре B2B-Center стенд не подключён.
- Внешние адреса внутренних служб в standalone формируются как loopback; для подключения другого Prometheus нужна отдельная настройка размещения.
- Сохранены контрольные документы HTTP-приёмки; база ради демонстрации не очищалась.

## Сценарий для проверяющих: 5–7 минут

1. Войти выделенным инженером по публичной ссылке (30 с).
2. Открыть «Источники», увидеть API ready и Prometheus online; выбрать «Аварийные события», дождаться опроса (до 45 с).
3. Открыть событие PostgreSQL: проверить тип, категорию, P1, объяснение и регламент с источником (1 мин).
4. Для нового эпизода принять решение, отметить выполнение вручную, открыть журнал; повтор не создаёт дубликат (1 мин).
5. В «Базе знаний» загрузить examples/reviewer-queue.json, дождаться succeeded; найти «Заказы стоят, обработчик не забирает сообщения» (1–2 мин).
6. Нажать «Восстановление», дождаться изменения событий; ручная история остаётся (до 45 с).
7. Обновить страницу и убедиться, что сессия сохранилась. Подробности PDF и большого импорта — в приложенном HTTP-отчёте (30 с).
