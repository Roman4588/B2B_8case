# Доработка надёжности кейса 8

Ветка: `fix/case8-reliability`. Исходная версия: `cc88c19184ec12acaaffe7f94b3268bd4b887b6a`.

## Поведение после изменений

- Сообщение «PostgreSQL is down; backup completed successfully» остаётся критическим P1.
  Отрицания успеха и противоречивые формулировки требуют проверки инженера. Классификатор
  по-прежнему использует метки, правила и текстовую модель; универсальное понимание текста
  и точность на произвольных событиях не заявляются.
- Правила больше не присваивают фиксированные 90–92% уверенности. Карточка показывает
  основание автоматического разбора и необходимость ручной проверки, без ложной вероятности.
- Восстановленный инцидент сохраняет прежние решения и аудит. Следующая авария создаёт
  новый эпизод. Изменение `activeAt` обнаруживает повтор даже между опросами.
  Если Prometheus не прислал корректный `activeAt`, используется время первого наблюдения;
  повтор без наблюдаемого восстановления и без времени источника распознать невозможно.
- Подключение переходит в состояние «Данные мониторинга устарели» после 60 секунд
  без успешного опроса. Ошибка запроса к API также убирает зелёный индикатор.
- При изменении события или базы знаний старые рекомендации очищаются. Результат
  фонового поиска публикуется только для актуального поколения запроса. Ошибка модели
  отображается отдельно, доступна кнопка повтора.
- Maintenance держит advisory lock на отдельном соединении до конца обработки,
  включая промежуточные commit. Медленный проход не пересекается со следующим проходом beat.
- Поиск сначала выбирает лучший фрагмент каждого регламента и затем ограничивает число
  документов. Один большой файл больше не занимает все 50 мест кандидатов.
- Несколько строк «Если X → Y» в TXT/MD и извлечённом тексте PDF/DOCX становятся
  отдельными инструкциями, сохраняя многострочные действия.
- В ленте доступны приоритет и статус ручной обработки. При истечении сессии приложение
  возвращает пользователя на вход. Мелкие подписи увеличены, мобильный верх сокращён.

## Обновление существующей базы

Обычный `docker compose up --build` запускает миграцию `0002` через init-сервис.
Она добавляет `recommendation_generation` со значением 0, сохраняя инциденты и решения.
Не удаляйте Docker-тома для обновления. Перед обновлением рабочего стенда сделайте резервную копию.

Первая миграция использует замороженную схему из `migrations/initial_schema.py`,
поэтому новый столбец создаётся второй миграцией и на чистой базе, и на существующей.
Уже утраченные прежней версией эпизоды восстановить этой миграцией нельзя.

## Проверка

Добавлены регрессии для смешанных событий и отрицаний, повторных аварий, нескольких
правил, устаревшего результата поиска, ошибки модели, свежести подключения,
фильтров и сохранения существующих данных при миграции.

Локальная проверка выполнялась на Windows с Python 3.12 и Edge:

- Классификация на опубликованном наборе: 48/48, итоговая accuracy тройки 100%.
  Это авторский набор исходного проекта, не независимая оценка и не гарантия 90% на новых данных.
- Backend/API и миграция: 37 тестов прошли, 6 интеграционных проверок пропущены.
- TypeScript и production build проходят. Сохранилось предупреждение Lucide о `use client`.
- Четыре браузерных регрессии проверяют заданные ответы API: сокрытие старых советов,
  повтор после ошибки, устаревшее подключение/фильтры, мобильную раскладку без overflow.
  Эти проверки дополняют существующие `operator.spec.ts` с настоящим стеком.

Docker и WSL здесь отсутствуют: шесть PostgreSQL/ONNX-интеграций локально пропущены.
Полный запуск с миграциями, pgvector и моделью необходимо проверить в существующем CI
после отправки ветки или на компьютере с Docker. Предыдущие отчёты и медиа в `docs/`
относятся к исходной версии и не заменяют эту проверку.

Команды:

```bash

cd frontend
```
