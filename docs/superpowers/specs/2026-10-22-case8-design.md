# ИИ-Ассистент Дежурного — спецификация решения кейса 8

Дата: 22 октября 2026 года.
Репозиторий: https://github.com/Roman4588/B2B_8case
Статус: согласована пользователем 22 октября 2026 года; план реализации подготовлен отдельно.

## 1. Цель и исходные материалы

Создать готовое приложение для кейса 8 из презентации «Презентация - мероприятие ТПУ.pptx»:
автоматически получать события мониторинга, определять тип, категорию и приоритет,
подбирать инструкции из базы знаний и помогать дежурному принимать решения.
Действия над инфраструктурой выполняет только человек.

Основание: слайды 30–32 (кейс 8), 5–6 (общие технические требования), 7 (материалы сдачи).
На слайде 28 ошибочно указан номер 8 внутри раздела про аудит безопасности:
этот слайд относится к соседнему кейсу 7 и не определяет содержание настоящего проекта.

Подтверждённые условия пользователя:
- всё выполненное сохраняется в B2B_8case;
- готового мониторинга и размеченного набора событий нет;
- при необходимости можно использовать диск C, предпочтение размещения объёмных данных на D;
- нужны готовый проект и понятная инструкция запуска;
- регистрация и платные API не нужны для выбранного решения.

## 2. Подход и альтернативы

Выбран локальный Docker Compose стенд с реальным Prometheus и демонстрационными метриками.
События проходят тот же API и обработку, которые используются при подключении внешнего мониторинга.

Рассмотренные альтернативы:
1. Локальная модель и Docker Compose — воспроизводимость, отсутствие ключей и расходов,
   сохранение событий внутри стенда. Требует первоначальной загрузки контейнеров и модели.
2. Внешний LLM API — гибкие объяснения, но требуются ключ, подключение к сети, расходы
   и решение вопроса передачи инфраструктурных данных третьей стороне.
3. Только регулярные выражения и SQLite — проще установка, но такой вариант не покрывает
   общие требования PostgreSQL и векторного поиска и не выбран.

Нейросетевой поиск используется для рекомендаций. Команды не генерируются произвольно:
показываются действия из загруженного регламента с источником.
Классификатор комбинирует текстовую модель и достоверные метаданные источника.

## 3. Стек

- Интерфейс: React, TypeScript, Vite; адаптивная SPA на русском языке.
- API: Python 3.12, FastAPI, Pydantic, SQLAlchemy, миграции Alembic.
- Хранилище: PostgreSQL 17 и расширение pgvector.
- Фоновые задачи: Celery и Redis; планировщик Celery Beat.
- Эмбеддинги: FastEmbed/ONNX Runtime,
  sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2, 384 измерения.
- Классификация: обучаемая текстовая модель с отдельно проверяемыми метками;
  нормализация severity источника и явная политика приоритетов.
- Мониторинг: Prometheus HTTP API; демонстрационный источник метрик.
- Доставка интерфейса и проксирование API: Nginx.
- Проверки: pytest, интеграционные тесты PostgreSQL/Redis,
  проверка TypeScript и сборка интерфейса, Playwright для пользовательского сценария.

Версии зависимостей фиксируются в файлах зависимостей при реализации.
Модель запускается на CPU; GPU, аккаунт в облаке и платный LLM не требуются.
Наличие модели и её загрузка видны в состоянии готовности системы.
При недоступности модели интерфейс показывает ошибку; подмена семантического поиска
необозначенными фиктивными результатами недопустима.

## 4. Компоненты и движение данных

Сервисы Compose:
- frontend: интерфейс и единая точка входа;
- api: REST API и OpenAPI;
- db: PostgreSQL/pgvector, профили, события, регламенты, задания, журнал;
- redis: брокер очереди;
- worker: классификация, индексирование и импорт;
- beat: периодический опрос источников;
- prometheus: настоящий экземпляр мониторинга;
- demo-exporter: управляемые демонстрационные метрики.

Поток события:
Prometheus → GET /api/v1/alerts → нормализация и дедупликация →
сохранение → очередь → классификация → векторный подбор регламентов →
сохранение результата → обновление дашборда.

Поток документа:
загрузка → сохранение задания → HTTP 202 с идентификатором →
фоновое извлечение текста и разбиение на фрагменты → эмбеддинги →
pgvector → готовая база знаний.

## 5. Пользовательские сценарии

### Дашборд

Пользователь видит активные события, количество по уровням критичности,
состояние подключения и время последнего обновления.
Есть фильтры по категории, типу, приоритету, статусу и тексту.
Типы: критическое, предупреждение, информационное.
Категории: сервер, сеть, БД, приложение.
Приоритеты: P1–P4; политика отображается в документации и объяснении классификации.

Карточка события показывает описание, источник, хост, время, метки,
результат классификации, уверенность/оценку модели и основание приоритета.
При недостаточной уверенности виден запрос на ручную проверку.
Незнакомые события не получают выдуманную инструкцию.

### Рекомендации и ручное подтверждение

Пользователь видит до трёх релевантных инструкций, источник и оценку сходства.
Сходство поиска не выдаётся за вероятность правильности.
Каждая инструкция содержит условие, последовательность действий и предупреждения.
Пользователь может отметить «Принято к ручному выполнению» и затем «Выполнено вручную»,
оставить комментарий или отклонить рекомендацию.

Подтверждение меняет только запись в приложении и создаёт запись аудита.
Приложение не содержит SSH-клиента, запуска shell-команд, вызова remediation API,
автоматического перезапуска сервисов или блокировки адресов.
Команды в регламенте являются текстом для самостоятельного выполнения инженером.

### База знаний

Создание и редактирование инструкции через форму «Если X → Y».
Импорт JSON, Markdown, TXT и текстовых PDF/DOCX.
Для PDF/DOCX больше 50 страниц используется очередь с отслеживанием прогресса.
Скан без текстового слоя распознаётся как неподдерживаемый ввод с понятным сообщением;
OCR не указан среди требований кейса.
Пользователь видит состояния: в очереди, обработка, готово, ошибка.
Документы и фрагменты доступны для поиска; инструкция может быть обновлена и переиндексирована.
Начальные регламенты включают CPU, память, диск, Nginx, сеть и PostgreSQL.

### Источники и журнал

Интерфейс показывает доступность Prometheus, последнюю успешную синхронизацию,
число полученных событий и понятную причину ошибки.
Адрес внешнего Prometheus и параметры доступа задаются через окружение.
Повторный опрос не создаёт дубликаты.
Исчезновение firing alert после успешной синхронизации фиксируется как восстановление;
ошибка источника не закрывает существующие инциденты.

Хранятся профиль инженера, комментарии и журнал действий.
Учётная запись для локального демонстрационного стенда создаётся при инициализации.
Внешняя публикация потребует смены демонстрационных реквизитов и HTTPS;
публикация в интернет не входит в текущую задачу.

## 6. Обработка ошибок и сохранность

- Схемы проверяют входные данные; ограничиваются размер и тип загружаемого файла.
- Файлы получают внутренние безопасные имена; пользовательский путь не используется.
- Очередь использует JSON и идемпотентные операции; задания имеют ограниченное число повторов.
- Ошибки подключения, обработки файла и модели сохраняются и показываются пользователю.
- Закрытие окна не прерывает уже принятое фоновое задание.
- Миграции выполняются до запуска API/worker; сервисы имеют проверки здоровья.
- PostgreSQL, загруженные файлы и модель сохраняются в отдельных томах.
- Секреты и пользовательские данные не коммитятся в GitHub.
- Сетевые интеграции имеют таймауты и проверяют TLS.
- Приложение не выполняет инструкции из текста события как программные команды.

## 8. Проверка точности

Тестовый набор хранится отдельно от обучения и демонстрационных данных.
Разделение производится по сценариям/семействам формулировок, чтобы близкие перефразировки
не попадали одновременно в обучение и проверку.
Набор охватывает все 3 типа, 4 категории, приоритеты P1–P4, русский и английский текст,
события с метками источника и события без явных меток.
Разметка и правила приоритетов доступны для проверки.

Команда оценки выдаёт размер набора, точность типа, категории, приоритета,
точность всей тройки и матрицы ошибок.
Порог приёмки — минимум 90% полностью верных троек на этом наборе;
отдельные метрики также публикуются.
При недостижении порога работа продолжается, результат не объявляется выполненным.

Разработанный вместе с проектом набор проверяет воспроизводимость и известные сценарии.
Он не заменяет независимую проверку организаторов на неизвестных событиях:
гарантия 90% на не предоставленном датасете без его оценки невозможна.
В отчёте обязательно указываются происхождение набора и это ограничение.

## 9. Запуск и ресурсы

Основной запуск: docker-compose up --build.
Для актуальной установки Compose также документируется docker compose up --build.
После готовности сервисов интерфейс доступен по localhost, API — через тот же адрес.
Начальные данные и реальный мониторинг включены в стандартный стенд.

На момент обследования: C свободно около 6 ГБ, D около 125 ГБ.
Исходники находятся в рабочей папке пользователя на C.
Кэши, модель и контейнерные диски желательно хранить на D.
Системные каталоги и существующие данные пользователя не перемещаются.
Docker CLI в PATH и стандартном каталоге установки не обнаружен;
вызов WSL в текущей среде вернул отказ в доступе.
Установка Docker/WSL может потребовать прав администратора и перезагрузки.
Без доступного Docker нельзя заявлять проверенный полный запуск контейнерного стенда.
Проверенные и не проверенные части будут явно разделены в итоговом отчёте.
