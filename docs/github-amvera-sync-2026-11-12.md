# Доставка текущих доработок в GitHub и Amvera

## Привязка

- GitHub: https://github.com/Roman4588/B2B_8case, основная ветка main. Перед интеграцией fetch подтвердил базу 875dfc8b7f91f26016d87bc0c301556312dcbdb2 без новых коммитов. Защита main не включена; прямой fast-forward push разрешён пользователем.
- Существующее приложение Amvera: madaminchyk/b2b, регион mia0. Новый ресурс не создаётся.
- В панели уже привязан webhook. Выделенный Git Amvera имеет HEAD на master; GitHub использует main, прежний SHA обоих репозиториев совпадает. Перед push готовится резервная копия, поскольку push может автоматически запустить обновление. При автоматическом запуске второй запуск сборки не нужен.
- Действующая конфигурация: deploy/amvera/Dockerfile.standalone, порт80, постоянный /data, одна реплика. Переменные, домен и тариф сохраняются.

## Проверки и состав

Итоговая версия: 108 backend-тестов пройдены, включая PostgreSQL, pgvector и миграцию 0004; production build frontend и полный Playwright 35/35 (2,8 мин). Первый повтор браузера после пересоздания API дал 5 ошибок входа из-за старого адреса upstream в локальном Nginx; после штатного restart frontend все 35 прошли без изменения тестов.

Настоящий standalone-образ проверен в контейнере 950 MiB / 0,5 CPU с новым тестовым томом и холодной загрузкой модели. Первый запуск выявил OOM: получение стоп-слов загружало sklearn/SciPy в API и worker. Те же 318 слов сохранены в данных с лицензией; добавлена регрессия отсутствия тяжёлого импорта. Исправленный контейнер не был OOMKilled и прошёл вход, реальные рекомендации, ручное подтверждение, идемпотентность, PDF60 и выход. Ответ импорта 0,086 с, полная обработка 18,483 с. Тариф и лимиты не повышались.

Дополнительный Ruff выявил 8 замечаний сортировки импортов в существующих тестовых файлах. Проверка не входит в текущий CI; несвязанные файлы ради сортировки не менялись. Новая регрессия импорта не имеет замечаний.

Передаются функции обратной связи, миграция0004, экспорт/метрики, исправления импорта, согласованный дизайн и unslop, регрессии и документация. .env, секреты, рабочие данные, модели, кеши, node_modules, outputs, traces, логи и случайные test-documents не добавляются. Видео сохраняется без изменения. Исходный diff и новые файлы сохранены вне репозитория до коммитов.

## Резервная копия и миграция

До доставки кода приложение штатно останавливается, после чего через интерфейс Amvera готовится и скачивается свежий архив Data. Проверяются ZIP/CRC, наличие postgres/PG_VERSION, global/pg_control, сохранённого файла пароля и uploads; секреты и содержимое БД не публикуются. Архив остаётся локально вне репозитория. Штатное хранилище и экспорт описаны в [документации Amvera](https://docs.amvera.ru/applications/storage.html).

Миграция0004 аддитивна: новые таблицы исправлений/оценок и nullable-поля аудита. Старые записи, аккаунты и регламенты сохраняются; прежние миграции не менялись. Перед восстановлением архивной Data остановить все процессы приложения. Не выполнять downgrade0004 на заполненной базе: это удалит новые данные. Старый образ 875dfc8 знает только ревизии до0003: простой выбор старого образа на БД0004 может остановить bootstrap с неизвестной ревизией. Для отката кода нужен совместимый образ, сохраняющий миграцию0004 и расширенную схему. Восстановление Data из архива согласовывается отдельно с учётом записей после создания копии; автоматический откат с потерей новых данных не применяется.

## Подтверждение версии

После push сверить SHA origin/main и полный перечень новых файлов. В Amvera проверить SHA сборки и признак используемой версии, затем публичные live/ready, авторизацию и основные экраны. Сверить имена JS/CSS с проверенной сборкой. Новые функции проверять только на созданных для проверки объектах; существующие события и документы не исправлять и не удалять.

Точный итоговый SHA, результат сборки/старта и послерелизных проверок фиксируются в итоговом сообщении и локальном протоколе доставки. Один зелёный статус сборки или страница входа не подтверждают синхронизацию.
